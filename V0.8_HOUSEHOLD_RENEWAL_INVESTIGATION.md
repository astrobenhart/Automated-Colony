# v0.8 Household Formation & Population Renewal Investigation

Date: 2026-06-27
Branch: v0.8-development

## Executive Summary

The Residential Growth Model is not structurally dead.

The original release validation used `World.advance_day()` directly. That path runs daily settlement, social, lifecycle, renewal, partnership, and birth systems, but it does not run the tick-level villager task execution loop where builders move, gather/build, and complete houses. As a result, household split or expansion demand can be generated for years without any homes being built.

When the same seed is run through the normal tick-level `World.update()` loop, residential growth activates:

- Seed 8201
- First residential demand: day 442, year 6, `expand_house`
- First new house tile built: day 446, year 6
- First household split: day 1249, year 16

Root cause: validation harness / scheduling mismatch, not a broken Residential Growth Model.

Confidence: High for the zero-split finding. Medium for the 100-year population decline until a tick-level long-run validation is performed.

## Housing Planner Analysis

The planner does receive residential demand.

Evidence from daily probe:

- Seed 8201 had `split_household` demand for 26 sampled years.
- Seed 8202 had residential demand for 68 sampled years: 13 split years and 55 expansion years.
- Seed 8203 had residential demand for 78 sampled years: 6 split years and 72 expansion years.

The construction planner creates building priorities from this demand through `src/building_priorities.py`.

The problem is not demand generation. The problem is that direct `advance_day()` validation does not run:

- villager role execution
- movement to build sites
- wood/material handling
- build progress
- `complete_residential_construction()`

## Behavioural Timeline Examples

Aggregate behaviour from seed 8201:

- Year 2-6: partnered founding adults produce early births.
- Year 6: first overcrowded household creates `expand_house` demand in tick-level simulation.
- Day 446, Year 6: builders complete a new house tile.
- Year 16: the first household split completes in tick-level simulation.
- Year 22 onward: adult children appear and become part of the partnership/split candidate pool.

In daily-only validation, the same demand exists but never resolves into a home or split.

## Root Cause Analysis

Primary cause: scheduling / validation architecture.

`World.advance_day()` is a calendar fast-forward. It calls daily systems, but it bypasses the per-tick `World.update_villagers_for_tick()` path. That makes it useful for lifecycle and history smoke tests, but not sufficient for validating construction-driven systems.

Relevant locations:

- `src/world.py`: `update()` runs tick-level villager work and calls `advance_day()` every day.
- `src/world.py`: `advance_day()` runs only daily updates.
- `src/residential.py`: `residential_demand()` correctly produces `expand_house` and `split_household` demand.
- `src/building_priorities.py`: `highest_priority()` converts residential demand into building priority.
- `src/task_behavior.py`: builder task progress eventually calls `complete_residential_construction()`.
- `src/residential.py`: `complete_residential_construction()` assigns new house tiles and can call `maybe_split_household_for_new_home()`.

Secondary concern: daily validation is still useful for detecting demographic pressure, but it should not be treated as proof that construction, expansion, or household splits are broken.

## Recommended Architectural Fix

Smallest fix:

Create an explicit long-run validation mode that advances days while also resolving scheduled tick-level work slices, especially construction.

Recommended approach:

1. Keep `advance_day()` as a pure daily/calendar path for tests that only need daily systems.
2. Add a validation/simulation runner that advances by ticks or by a faithful accelerated tick loop.
3. For long-run release validation, use this runner instead of direct `advance_day()`.
4. Record whether residential demand was generated, whether build progress occurred, and whether construction completed.

Do not increase birth probability yet.

Only tune demographics after a true tick-level or accelerated-work validation confirms population still declines when residential construction and splits are allowed to complete.

## Proof-of-Concept Validation

Command:

```powershell
python tools\probe_tick_household_construction.py --seed 8201 --max-days 3000
```

Result:

- First demand: day 442, year 6, `expand_house`
- First house increase: day 446, year 6
- First household split: day 1249, year 16
- Population at split: 56
- Births by then: 13
- Deaths by then: 2

This confirms that enabling natural household formation through the normal tick loop produces more housing and at least one new household without changing birth probability or demographic constants.

## Confidence Level

High confidence:

- Zero splits in the previous release validation are caused by daily fast-forward bypassing tick-level construction.
- Residential demand reaches the planner.
- Tick-level construction can build new homes.
- Tick-level simulation can complete household splits.

Medium confidence:

- v0.8 century-scale population stability remains unproven until a tick-faithful 50/100-year validation is run.

## Next Step

Replace the release validation harness with a tick-faithful or accelerated-work runner, then rerun:

- 3 independent 50-year simulations
- 3 independent 100-year simulations

Only after that run should the team decide whether population decline is a real balance issue or an artifact of incomplete validation execution.
